Who reads this code?

Programmers do not read code like a page of text, and no two read it alike. This project measures how they read it, with eye-tracking data from 185 programmers, and tests whether an AI explanation can adapt to one developer without changing what it should not.

The question

AI coding assistants explain, test and generate code in the same way for everyone. Yet experience changes where programmers look and in which order: experts read code less linearly than novices (Busjahn et al., 2015). In text reading, how long the eyes rest on a word tracks how predictable that word is (Demberg and Keller, 2008). If the same holds for code, and if readers fall into recognisable types, an assistant could learn who is reading and adapt. That raises a second question: when an assistant is told about a developer, does its explanation change only where it should?

The hypotheses and analysis plan were written down before the gaze data were loaded, and every result is reported whether it supports them or not.

Data

EMIP, the Eye Movements in Programming dataset (Bednarik et al., 2020), recorded 216 programmers reading two short Java, Python or Scala programs with a 250 Hz eye tracker. It ships the screen position of every code token, so gaze can be matched to tokens exactly. After preregistered exclusions, the analysis keeps 351 Java reading sessions from 185 programmers: 44,912 token observations.

Finding 1: surprising code is read longer

Tokens that a code language model finds less predictable are read about 4 ms longer per bit of surprisal. Mixed-effects model on total reading time, controlling for token length, position and frequency: p < .001. The effect holds in each program on its own.
Two predictions did not hold. The effect was not weaker for experts (p = .48), and predictable tokens were not skipped more often (p = .11).

Finding 2: two ways of reading code

Readers split into a linear type and a non-linear type, and the non-linear type is more common among experienced programmers. Kruskal–Wallis p = .03; the types did not differ in comprehension accuracy. Exploratory.

Finding 3: telling a model about a developer changes more than it should

A developer profile marks constructs such as constructors, this. fields or new as known or unknown. Flipping one construct to “known” should change only the lines that use it. Two systems were compared with the same language model:

SystemLines using the construct that changedOther lines that changed
Profile pasted into the prompt40 %13 %
Notes written once, then selected per line by an RSA-style speaker69 %0 %

Rerunning the prompt-only system with an unchanged profile changed at most 2.5 % of lines, so the 13 % is leakage, not noise. Separating what to explain, chosen from the profile with a literal listener in the Rational Speech Acts framework (Goodman and Frank, 2016), from how to say it keeps the adaptation where it belongs.

Limits

Two short programs; self-rated expertise; random intercepts only. The fixation detector splits long fixations, so absolute durations are short. The explanation experiment tests where explanations change, not whether developers understand them better: nobody has read the generated notes yet. EMIP has no EEG, and the demo’s rule for flagging difficult lines is simple and unvalidated.
